# План: настраиваемый скоринг при публикации вакансии

> Документ только про проектирование. Реализация — после вашего согласования.
> Отвечает на два вопроса: **готов ли продукт к живому тесту без API** и
> **как правильно сделать изменяемые критерии**.

---

# Часть A. Готовность к тесту без API

Короткий ответ: **нет, дело не только в API.** Готовность примерно 70%.

| Блок | Готов | Что значит |
|---|---|---|
| Архитектура, домен, порты, адаптеры | **да** | каркас выдерживает подключение каналов |
| Адаптер hh.ru | **да** | OAuth, отклики, чат, резюме, приглашение — по документации |
| Адаптер Talantix | **да** | занятость, слоты, бронь, верификация |
| Адаптер Avito | **каркас** | нужен контракт API |
| Безопасность: SQLi, async, кэш, ПДн | **да** | 572 теста |
| Воронка: анализ → вопросы → приглашение | **да** | без настраиваемого скоринга |
| **Скоринг в % с уверенностью и блокерами** | **нет** | только балл 0–100 |
| **Приоритизация «кому первым»** | **нет** | обработка в порядке поступления |
| **Изменяемые критерии при публикации** | **нет** | критерии в БД, без экрана и версий |
| **Логика ≤5 вопросов** | **частично** | обрезка в адаптере, без выбора и стоп-правил |

## Что проверится только вживую

Эти вещи **нельзя** закрыть без ключей — и это нормально:

1. OAuth-флоу hh.ru: реальный `redirect_uri`, домен, HTTPS;
2. фактические имена полей в ответах — меппере могут потребовать правки;
3. какие `actions[]` реально приходят в откликах;
4. права на резюме: `403` vs `404` vs квота на вашем тарифе;
5. реальные лимиты и `Retry-After`;
6. Talantix: доступен ли API на тарифе, валидирует ли конфликты.

## Что можно и нужно сделать **до** ключей

Пункты 10–13 из ваших новых вводных — они не зависят от площадок:

- скоринг в процентах с уверенностью и блокерами;
- приоритизация с предскорингом;
- настраиваемые критерии и вопросы;
- логика ≤5 вопросов.

**Именно это делает продукт «боевым» до вставки ключей.** После ключей
останутся только приёмочные правки по реальным ответам API, а не переделка логики.

# Часть B. Как сделать настраиваемые критерии

## B1. Главный принцип

Критерий — это **данные, а не код**. Сейчас так и есть (`vacancies.criteria`
как JSON), но нет способа их менять и нет версий. Значит нужно добавить:

1. **Профиль скоринга** — версионируемый набор: критерии + вопросы + пороги.
2. **Экран настройки** — где рекрутер это собирает.
3. **Публикацию** — черновик превращается в версию, которая применяется к новым
   кандидатам.

Ключевое правило: **изменение профиля не затрагивает уже обработанных
кандидатов**. Решение по каждому хранит, по какой версии оно принято.

---

## B2. Ответ на ваш вопрос: чекбоксы или список с галочками

**Ни то, ни другое в чистом виде.** Нужен мультивыбор с галочками **плюс**
два параметра на каждый выбранный критерий.

Почему чекбокса недостаточно:

| Что нужно задать | Почему это не чекбокс |
|---|---|
| Выбран ли критерий | чекбокс — да |
| **Вес** (насколько важен) | число: 1 / 2 / 3 |
| **Обязательность** (провал = потолок) | переключатель: да/нет |

Один чекбокс отвечает только на первый вопрос. Если сделать «важность через
чекбоксы» — получится непонятно: два отмеченных критерия равны? Или первый
важнее? Это классическая ошибка.

**Правильная схема: список с галочками + панель выбранных с настройкой.**

---

## B3. Как выглядит экран (три шага)

### Шаг 1. Критерии

```
┌─ Критерии вакансии ─────────────────────── Выбрано: 5 ─┐
│ [поиск: ______________]      только выбранные ▾       │
│                                                        │
│ ▾ Опыт и стаж                                          │
│   ☑ Стаж по профилю вакансии          [вес 1|2|3] [обяз.]│
│   ☐ Общий стаж работы                                  │
│   ☐ Опыт в отрасли                                     │
│                                                        │
│ ▾ Навыки и технологии                                  │
│   ☑ Python                             [вес 1|2|3] [обяз.]│
│   ☑ SQL и реляционные базы             [вес 1|2|3] [обяз.]│
│   ☐ Docker                                             │
│                                                        │
│ ▾ Условия работы                                       │
│   ☑ Готовность к удалённой работе      [вес 1|2|3] [обяз.]│
│                                                        │
│ [+ Добавить свой критерий]                             │
└────────────────────────────────────────────────────────┘
```

Решения по UX и почему так:

| Решение | Почему |
|---|---|
| **Галочка = выбрать критерий** | привычно, быстро, безDrag&drop |
| **Вес — переключатель 1/2/3**, а не поле ввода | три значения читаются мгновенно; свободное число провоцирует «10 из 10» |
| **Обязательность — переключатель** | видно, что провал даёт потолок |
| **Категории свёрнуты** | 43 критерия — это стена, если показать всё |
| **Поиск по каталогу** | когда критериев много |
| **Фильтр «только выбранные»** | проверка перед публикацией |
| **Счётчик выбранных** | контроль объёма |
| **«Добавить свой критерий»** | каталог не покрывает всё; нужен путь без разработчика |

Для своего критерия обязательны три поля: название, **что искать в резюме**
(иначе модель не поймёт, что считать доказательством), вес, обязательность.

### Шаг 2. Вопросы (не более 5)

```
┌─ Вопросы кандидату ─────────────── Выбрано: 3 / 5 ─────┐
│ Вопросы привязаны к выбранным критериям.               │
│                                                        │
│ Критерий: SQL и реляционные базы                       │
│  ☑ Работали ли вы с PostgreSQL? Что делали?            │
│  ☐ Какие объёмы данных обрабатывали?                   │
│                                                        │
│ Критерий: Готовность к удалённой работе                │
│  ☑ Готовы работать удалённо?                           │
│                                                        │
│ Критерий: Python                                       │
│  ☑ Какой опыт с асинхронным Python?                    │
│  ☐ Использовали ли FastAPI?                            │
│                                                        │
│ ☐ Задать свой вопрос                                   │
│                                                        │
│ ⓘ При 5 выбранных новые недоступны.                    │
│ ⓘ Бот может остановиться раньше, если решение ясно.    │
└────────────────────────────────────────────────────────┘
```

| Решение | Почему |
|---|---|
| **Вопросы сгруппированы по критериям** | видно, какой пробел закрывает вопрос |
| **Счётчик 3 / 5 и блокировка при 5** | требование «не больше 5» видно в интерфейсе, а не только в коде |
| **Подсказка про ранний выход** | чтобы не думали, что бот обязательно задаст все 5 |
| **Свои вопросы** | реальные вакансии требуют своих формулировок |
| **Импорт из шаблона** | «сменить часть вопросов» — это правка 2–3 из 5, а не ввод с нуля |

### Шаг 3. Пороги и предпросмотр

```
┌─ Решение ──────────────────────────────────────────────┐
│ Пригласить от:      [ 85 ] %                           │
│ Передать человеку:  [ 55 ] %  (от … до приглашения)    │
│ Отказ ниже:         [ 40 ] %                           │
│                                                        │
│ ☐ Приглашать автоматически (иначе — только апрув)      │
│                                                        │
│ Предпросмотр: 5 критериев, 3 вопроса, порог 85%        │
└────────────────────────────────────────────────────────┘
```

Почему три порога, а не один: между «пригласить» и «отказать» должен быть
коридор, где решает человек. Иначе бот отказывает тем, кого вы бы взяли.

---

## B4. Модель данных

```
ScoringProfile              — профиль вакансии
  id, vacancy_id, version, status(draft|published|archived),
  created_by, created_at, published_at, comment

ProfileCriterion            — выбранный критерий профиля
  id, profile_id, key, title, weight, must_have,
  evidence_hint, source(catalog|custom), position

ProfileQuestion             — вопрос профиля
  id, profile_id, criterion_key, text, kind, position,
  informativeness(1..3), is_custom

ProfileThresholds           — пороги профиля
  profile_id, invite_at, human_at, reject_at, auto_invite
```

Связи:

- у вакансии — **активный профиль** (одна published-версия);
- при публикации новой версии старая уходит в `archived`, но **остаётся** для
  истории;
- `screenings` получает поле `profile_version`, чтобы решение было объяснимо
  задним числом.

Вопросы **не хранятся в промпте**: промпт собирается из `ProfileQuestion`. Это и
есть «сменить часть вопросов» — меняются данные, не код.

---

## B5. Версионирование: как не сломать историю

| Действие | Что происходит |
|---|---|
| Рекрутер правит критерии | изменения копятся в **черновике** |
| Нажимает «Опубликовать» | создаётся версия N+1, она применяется к новым кандидатам |
| Кандидат обрабатывается | решение сохраняет `profile_version` |
| Смотрим старую карточку | видим версию, по которой считалось |
| Откат | «сделать активной версию N» — прежняя не удаляется |

Почему так: без этого нельзя ответить на вопрос «почему вчера бот отклонил
хорошего кандидата» — критерии уже другие.

---

## B6. Валидация (сервер + интерфейс)

| Правило | Почему |
|---|---|
| Хотя бы один критерий | иначе оценивать не по чему |
| Хотя бы один обязательный критерий | иначе нет блокеров, потолок не работает |
| Сумма весов > 0 | защита от деления на ноль |
| Вопросов ≤ 5 | требование |
| У каждого вопроса есть критерий | иначе вопрос ни на что не влияет |
| Нет критериев по защищённым признакам | `PolicyGuard` — уже реализован |
| Пороги: `reject < human ≤ invite` | иначе логика решения ломается |

Валидация **на сервере обязательна**, в интерфейсе — подсказки. Иначе
несогласованный профиль можно отправить руками через API.

## B7. API

```
GET    /api/v1/vacancies                        список
POST   /api/v1/vacancies                        создать
GET    /api/v1/vacancies/{id}/scoring           активный профиль + черновик
PUT    /api/v1/vacancies/{id}/scoring/draft     сохранить черновик
POST   /api/v1/vacancies/{id}/scoring/publish   опубликовать версию
GET    /api/v1/vacancies/{id}/scoring/versions  история версий
POST   /api/v1/vacancies/{id}/scoring/rollback  сделать активной версию N
GET    /api/v1/criteria/catalog                 каталог (уже есть данными)
```

## B8. Этапы

| Этап | Содержание | Проверяемо без API |
|---|---|---|
| **1** | Модель данных профиля + миграции | да |
| **2** | Скоринг в %: `percent`, `coverage`, `blockers` | да |
| **3** | Экран настройки: критерии (галочки + вес + обязательность) | да |
| **4** | Библиотека вопросов + экран выбора ≤5 | да |
| **5** | Публикация и версионирование профиля | да |
| **6** | Пороги + правило решения (пригласить / человек / отказ) | да |
| **7** | Приоритизация и предскоринг | да |
| **8** | Приёмочные правки после живых API | нет |

Этапы 1–7 готовят продукт к «вставить ключи и поехать». Этап 8 — уже с вашими
ключами.

---

## B9. Риски

| Риск | Что делаем |
|---|---|
| Критериев слишком много → скоринг «размазан» | предупреждение при >10 критериях, подсказка объединить |
| Веса «на глаз» | калибровка на эталонной выборке после пилота |
| Смена профиля ломает ожидания | версии + `profile_version` в решении |
| Свои критерии без `evidence_hint` | поле обязательно при добавлении |
| Рекрутер забыл опубликовать | статус «черновик» виден в списке вакансий |

## B10. Что нужно от вас до старта

1. **Согласовать схему экрана** (три шага, галочки + вес + обязательность) —
   или предложить свою.
2. **Взять ли пороги 85 / 55 / 40** как значения по умолчанию.
3. **Разрешить ли автоприглашение** (сейчас по умолчанию всё через человека).
4. **Кто публикует профиль** — рекрутер или только руководитель.
5. **Подтвердить, что критерии в демо убираем** (или заменяем на ваши).

Если план подходит — начинаю с этапов 1–2: модель профиля и процент с
уверенностью и блокерами. Остальное по порядку.
