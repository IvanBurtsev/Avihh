# План: скоринг в процентах, приоритетная очередь и лимит вопросов

> Документ описывает **логику и план работ**, без реализации.
> Основан на новых вводных: скоринг в процентах, приоритизация кандидатов,
> настраиваемость при публикации вакансии, не более 5 вопросов от бота.

---

## 1. Что меняется по сравнению с текущим прототипом

| Сейчас | Нужно |
|---|---|
| Балл 0–100, но без интерпретации и без очереди | **Процент соответствия** + понятные уровни + очередь «кому писать первым» |
| Критерии фиксированы в вакансии | **Настраиваемый профиль скоринга**, редактируемый при публикации |
| Бот задаёт вопросы по списку из модели | **Планировщик вопросов**: не более 5, по информационной ценности |
| После ответов пересчёт есть, но без явного решения | **Правило решения** после 5 вопросов: пригласить / человек / отказ |
| Обработка откликов в порядке поступления | **Приоритетная очередь** с учётом квот площадки |

Ключевое требование, которое меняет всё остальное:

> **Бот задаёт не больше 5 вопросов и затем принимает решение либо передаёт человеку.**

Это ограничивает не количество сообщений, а **объём информации, который мы
можем собрать до решения**. Значит вопросы должны быть не «любые из промпта»,
а **выбранные по ценности** — иначе пяти не хватит.

---

## 2. Скоринг в процентах

### 2.1. Что означает процент

Процент — это **взвешенное соответствие критериям вакансии**, а не «вероятность
найма». Формулировка для интерфейса: «соответствие 84%», не «подходит на 84%».

```
match_percent = Σ(оценка_критерия × вес) / Σ(вес)
```

Где `оценка_критерия` — 0…100 от модели **с обязательной цитатой** из резюме
или из ответа кандидата.

### 2.2. Процент — не единственное число

Рядом с процентом всегда показываются три вещи, иначе решение принимается вслепую:

| Показатель | Зачем |
|---|---|
| **percent** | насколько закрыты критерии |
| **уверенность** (`coverage`) | по скольким критериям есть данные: 4 из 6 = 67% |
| **блокеры** | провалы обязательных критериев, если есть |

Пример: «78% · данные по 4 из 6 критериев · блокеров нет» — это другой кандидат,
чем «78% · данные по 6 из 6», и решение по ним разное.

### 2.3. Шкала и что делать на каждом уровне

| Процент | Уровень | Что делает система |
|---|---|---|
| **85–100** | сильное соответствие | приоритет 1: пишем первым, приглашение без лишних вопросов |
| **70–84** | соответствует | приоритет 2: задаём уточняющие вопросы, приглашение по результату |
| **55–69** | на грани | приоритет 3: вопросы задаём, но приглашение — с апрувом человека |
| **40–54** | слабое | не пишем; отправляем человеку с обоснованием |
| **0–39** | не подходит | не пишем; отказ **только если включён** автоотказ, иначе человеку |

Два жёстких правила поверх шкалы:

1. **Провал обязательного критерия** → потолок 40% и уровень не выше «слабое»,
   каким бы высоким ни был средний балл.
2. **Нет данных по обязательному критерию** → не «не подходит», а
   «недостаточно данных» → вопросы или человек. Отсутствие информации нельзя
   трактовать как минус.

## 3. Приоритизация: кому писать первым

### 3.1. Почему нельзя просто сортировать по проценту

Три причины, из-за которых «сортировка по проценту» ломается:

1. **Квоты площадки расходуются на просмотр резюме.** У hh.ru — 500 просмотров
   в день. Если открывать резюме в порядке поступления, квота уходит на слабых.
2. **Лимит сообщений подряд** (5 у hh.ru) и суточные лимиты. Писать всем сразу
   нельзя даже при желании.
3. **Свежесть критична**: кандидат, откликнувшийся час назад, ждёт ответа;
   ответ через сутки — это уже «неактуально».

### 3.2. Двухступенчатый скоринг — экономия квоты

```
Отклик пришёл
   │
   ├─► 1. ПРЕДСКОРИНГ (сразу, без открытия резюме)
   │      по метаданным отклика: заголовок вакансии в резюме,
   │      город, зарплата, опыт, готовность к переезду
   │      → предварительный процент и место в очереди на открытие резюме
   │
   └─► 2. ПОЛНЫЙ СКОРИНГ (после открытия резюме)
          критерии + цитаты → финальный процент
```

Зачем: **открываем резюме тем, кто с большей вероятностью пройдёт**. Это
прямая экономия платных просмотров и времени.

Риск: предскоринг по метаданным **ошибается** (сильное резюме с бедным
заголовком). Поэтому:

- предскоринг не может **отклонить** кандидата — только поставить в очередь;
- кандидаты, до которых квота не дошла за сутки, переходят в очередь человека,
  а не теряются;
- метрика: доля кандидатов, у кого предскоринг и полный разошлись больше чем на
  25 процентных пунктов — следим, чтобы не «оптимизировать» вслепую.

### 3.3. Формула приоритета

```
priority = percent
         − штраф_блокер       (провал обязательного: −40)
         − штраф_неполнота    (нет данных по обязательному: −15)
         + бонус_свежесть     (до +10: чем новее отклик, тем выше)
         + бонус_быстрый_выход (+5, если кандидат готов выйти в ближайшие дни)
```

Сортировка очереди: `priority DESC`, при равенстве — `получен_раньше ASC`.

**Почему штрафы, а не отдельные очереди:** иначе получается «сначала все
сильные, потом все средние», и средние ждут сутками, хотя среди них могут быть
те, кого можно пригласить за 2 вопроса.

### 3.4. Бюджет квоты

| Ресурс | Правило распределения |
|---|---|
| Просмотры резюме (hh) | очередь по предскорингу; резерв 10% на «хвост», чтобы не отсечь ошибочно |
| Сообщения (лимит подряд) | строго по приоритету; при упоре — приоритет 3 ждёт |
| Вопросы (5 на кандидата) | не экономим, это наш ресурс, не площадки |

**Важно:** квота — общий ресурс на всех. Поэтому приоритизация должна считать
не «кого обработать первым», а «**кого обработать за доступный бюджет**».

## 4. Настраиваемость скоринга при публикации вакансии

### 4.1. Профиль скоринга

Отдельная версионируемая сущность, привязанная к вакансии:

```
ScoringProfileVersion
  ├── criteria[]        — критерии: ключ, вес, обязательность
  ├── questions[]       — пул вопросов с привязкой к критериям
  ├── thresholds        — пороги: пригласить / человек / отказ
  ├── priority_rules    — штрафы и бонусы
  └── version, author, created_at, comment
```

Вакансия ссылается на конкретную версию профиля. **Изменение профиля не
затрагивает уже обработанных кандидатов** — они посчитаны по той версии, что
действовала на момент обработки. В истории видно, по какой версии принято
решение (это уже заложено в `screenings.prompt_version`).

### 4.2. Что можно менять при публикации

| Меняется | Не меняется |
|---|---|
| Веса и обязательность критериев | История уже принятых решений |
| Пороги (пригласить / человек) | Уже отправленные вопросы |
| Пул вопросов и их приоритеты | |
| Формулировки вопросов под конкретную вакансию | |

### 4.3. Шаблоны и быстрое изменение

При публикации новой вакансии:

1. выбрать **шаблон** (например, «Продавец-кассир», «Python-разработчик»);
2. скорректировать критерии из каталога (`docs/CRITERIA-CATALOG.md`);
3. **заменить часть вопросов** — не с нуля, а точечно;
4. задать пороги;
5. опубликовать → создаётся новая версия профиля.

Требование «сменить часть вопросов» означает, что вопросы должны быть
**библиотекой с привязкой к критериям**, а не текстом в вакансии.

## 5. Вопросы: не больше пяти

### 5.1. Библиотека вопросов

Вопрос — сущность, а не строка:

```
Question
  ├── criterion_key      — какой критерий он уточняет
  ├── text               — формулировка
  ├── kind               — факт | предпочтение | условие | уточнение опыта
  ├── answers            — варианты (если закрытый) или свободный ответ
  ├── informativeness    — насколько ответ меняет решение (1–3)
  ├── cost               — насколько ответ неприятен кандидату (1–3)
  └── applies_to         — категории вакансий / семейства критериев
```

### 5.2. Как выбираются 5 вопросов

Не «первые пять из списка», а **максимизация информации за пять шагов**:

```
1. Берём критерии, где нет данных или данных мало (coverage < 1)
   и вес критерия высокий.
2. Отбрасываем то, что уже есть в резюме (не спрашиваем то, что видно).
3. Отбрасываем то, что нельзя улучшить вопросом
   (например, «опыт 5 лет» — это факт из резюме, а не вопрос).
4. Для оставшихся критериев берём вопросы с наибольшей
   informativeness / cost и ещё не заданные.
5. Ограничиваем 5 вопросами.
```

Оценка полезности вопроса:

```
value = informativeness × вес_критерия × (1 − текущая_уверенность)
```

Вопрос про обязательный критерий с нулевой уверенностью выигрывает у трёх
вопросов про второстепенные критерии, по которым данные уже есть.

### 5.3. Адаптивность: можно остановиться раньше

Пять — это **максимум, а не цель**. После каждого ответа:

- пересчитываем процент и уверенность;
- если решение уже однозначно (например, процент ушёл выше 85 и блокеров нет) —
  **прекращаем спрашивать** и приглашаем;
- если ответ противоречит резюме или открыл блокер — прекращаем и передаём
  человеку.

**Почему это важно:** лишние вопросы снижают конверсию ответа. Пять вопросов
подряд от бота — уже много; шесть-семь — кандидат закрывает чат.

### 5.4. Стоп-правила (обязательные)

| Условие | Действие |
|---|---|
| Провал обязательного критерия в ответе | стоп, передать человеку |
| Противоречие с резюме | стоп, передать человеку |
| Два непонятных/уклончивых ответа подряд | стоп, передать человеку |
| Кандидат задал встречный вопрос | ответить, счёт вопросов не тратить |
| Кандидат просит не задавать вопросы | стоп, передать человеку |
| Нет ответа 24 часа | одно напоминание, затем человеку |
| Достигнут лимит 5 | перейти к решению |

## 6. Решение после вопросов

```
Собрано ≤5 ответов → пересчёт процента и уверенности
        │
        ├─ percent ≥ порог_приглашения И нет блокеров И coverage ≥ 0.7
        │        → черновик приглашения (на апрув или авто — по настройке)
        │
        ├─ percent ≥ порог_приглашения, но coverage < 0.7
        │        → человеку: «данных мало, но кандидат перспективен»
        │
        ├─ порог_отказа ≤ percent < порог_приглашения
        │        → человеку с обоснованием и цитатами
        │
        └─ percent < порог_отказа
                 → отказ, если автоотказ включён; иначе человеку
```

Три обязательных условия для автоматического приглашения:

1. процент выше порога;
2. нет провалов обязательных критериев;
3. по обязательным критериям есть данные (не догадки).

Если хотя бы одно не выполнено — решение уходит человеку. Это и есть
требование «принимает решение **или** отдаёт человеку».

## 7. Что меняется в системе

### 7.1. Новые сущности

| Сущность | Назначение |
|---|---|
| `ScoringProfile` + версии | настраиваемый скоринг под вакансию |
| `Question` (библиотека) | вопросы с привязкой к критериям и ценностью |
| `QuestionPlan` | выбранные ≤5 вопросов на конкретного кандидата |
| `Answer` | ответ кандидата с привязкой к вопросу и критерию |
| `PriorityScore` | рассчитанный приоритет и его составляющие (объяснимость) |
| `QuotaLedger` | израсходованные квоты площадки (просмотры, сообщения) |

### 7.2. Новые сервисы

| Сервис | Ответственность |
|---|---|
| `PreScoringService` | предскоринг по метаданным, очередь на открытие резюме |
| `PriorityService` | расчёт приоритета, порядок обработки с учётом бюджета квоты |
| `QuestionPlanner` | выбор ≤5 вопросов, стоп-правила |
| `RescoringService` | пересчёт процента по ответам, решение |
| `ScoringProfileService` | версии профилей, публикация вакансии |

### 7.3. Изменения в существующем

| Компонент | Что меняется |
|---|---|
| `ScreeningService` | возвращает `percent`, `coverage`, `blockers` вместо одного балла |
| `ConversationService` | после вопросов вызывает `RescoringService` и правило решения |
| `PolicyGuard` | проверяет состав вопросов (нет вопросов о защищённых признаках) |
| UI: карточка кандидата | процент + уверенность + блокеры + «почему» |
| UI: новый экран | настройка профиля скоринга при публикации вакансии |
| UI: очередь | сортировка по приоритету, а не по дате |
| API | эндпоинты профилей скоринга и библиотеки вопросов |

### 7.4. Миграции

Потребуются новые таблицы (профили, вопросы, планы, ответы, приоритеты,
квоты). Существующие `screenings` расширяются полями `percent`, `coverage`,
`blockers`, `profile_version`.

## 8. Как проверить, что логика работает

### 8.1. Метрики качества скоринга

| Метрика | Что показывает | Целевое значение |
|---|---|---|
| Precision приглашений | доля приглашённых, дошедших до собеседования | измеряем, не гадаем |
| Доля автоприглашений без правки | насколько бот уверен | растёт со временем |
| Среднее число вопросов | эффективность планировщика | 3–4, максимум 5 |
| Доля «данных мало» | качество вопросов | должна падать |
| Расхождение предскоринга и полного | ошибка экономии квоты | < 25% кандидатов |

### 8.2. Проверка на эталонной выборке

Уже есть `data/evaluation/golden_set.json` и `hirebot evaluate`. Расширить:
добавить ожидаемые **приоритеты** и **число вопросов**, чтобы проверять не
только «пригласил/нет», но и «правильно ли очередь».

### 8.3. Проверка ограничений

| Проверка | Как убедиться |
|---|---|
| Не больше 5 вопросов | тест на планировщик: 20 критериев → не более 5 вопросов |
| Ранний выход | тест: после 2 ответов процент выше порога → вопросов больше не задаём |
| Стоп-правила | тест на каждое из 7 правил |
| Квоты | тест: бюджет 10 просмотров, 100 откликов → просмотрены самые приоритетные |

## 9. Риски

| Риск | Последствие | Что делаем |
|---|---|---|
| Веса заданы «на глаз» | скорректированный процент не отражает реальность | калибровка на эталонной выборке, пересмотр после пилота |
| Предскоринг ошибается | сильные кандидаты уходят в конец очереди | резерв квоты, эскалация «хвоста» человеку, метрика расхождения |
| Кандидат «подстраивается» под вопросы | процент завышен | вопросы про факты проверяемы, ответы сохраняются в истории |
| Вопросов много → кандидат уходит | падение конверсии | максимум 5 + ранний выход + счётчик вопросов как метрика |
| Оптимизация под метрику, а не под найм | «красивые» цифры, плохие решения | смотрим на долю дошедших до собеседования, а не на процент |
| Лимиты площадки | бот не успевает ответить | приоритетная очередь с бюджетом, честный SLA в интерфейсе |
| Квоты тратятся на слабых | деньги впустую | предскоринг + резерв + отчёт по расходу квоты |

## 10. Этапы работ

| Этап | Содержание | Результат |
|---|---|---|
| **1. Процент и приоритет** | `percent`, `coverage`, `blockers`; шкала уровней; очередь по приоритету | рекрутер видит, кому писать первым |
| **2. Профили скоринга** | версии профиля, шаблоны, пороги; публикация вакансии с настройкой | можно менять критерии и пороги под вакансию |
| **3. Библиотека вопросов** | вопросы с привязкой к критериям, ценность, стоимость | вопросы перестают быть текстом в промпте |
| **4. Планировщик ≤5** | выбор вопросов, ранний выход, 7 стоп-правил | бот спрашивает мало и по делу |
| **5. Решение после вопросов** | рескоринг, три условия автоприглашения, эскалации | цикл замкнут: вопросы → решение |
| **6. Квоты и бюджет** | учёт просмотров/сообщений, распределение | лимиты площадки не блокируют работу |
| **7. Экран настройки** | UI профиля скоринга при публикации | рекрутер настраивает сам, без разработчика |
| **8. Замер** | расширенная выборка с приоритетами | цифры вместо предположений |

Этапы 1–2 не зависят от доступов к площадкам и делаются сразу.
Этапы 3–5 — ядро логики, тоже без доступов.

## 11. Что нужно решить до реализации

| Вопрос | Почему важно |
|---|---|
| **Пороги** для ваших вакансий | 85/70/55/40 — стартовая гипотеза, нужно ваше мнение |
| **Кто утверждает профиль** при публикации | рекрутер или руководитель |
| **Автоприглашение** разрешено или только апрув | влияет на риски и на UX |
| **Что считается «блокером»** для ваших вакансий | какие критерии обязательны |
| **Максимум вопросов** — жёстко 5 или настраиваемо 3–5 | влияет на планировщик |
| **Поведение при молчании кандидата** | напоминание, срок, эскалация |
| **Бюджет квоты** на day: сколько просмотров готовы тратить | определяет приоритизацию |

---

## 12. Одной фразой

> Процент соответствия — это взвешенное закрытие критериев с обязательной
> цитатой; приоритет — процент с поправками на блокеры, неполноту данных и
> свежесть; вопросы — не более пяти, выбираются по информационной ценности и
> могут остановиться раньше; после ответов система приглашает только при
> выполнении трёх условий, иначе передаёт человеку.
