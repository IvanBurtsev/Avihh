# Пакет для получения доступов к площадкам

> **Зачем этот документ.** Критический путь проекта — не код, а одобрения.
> Модерация приложения hh.ru занимает до 15 рабочих дней, доступ к Avito API
> выдаётся по заявке, доступ к Talantix API зависит от тарифа. Всё это можно
> и нужно запускать параллельно с разработкой.
>
> Ниже — готовые к отправке тексты, точные адреса и вопросы, ответы на которые
> определяют объём работ.

---

## Сводка: что и где запрашиваем

| Площадка | Куда обращаться | Что просим | Ориентировочный срок |
|---|---|---|---|
| **hh.ru** | [dev.hh.ru/admin](https://dev.hh.ru/admin) | регистрация приложения работодателя | модерация **до 15 рабочих дней** |
| **Talantix** | личный кабинет → API-токены (нужен **администратор**) | токены + подтверждение тарифа | 1–3 дня, зависит от тарифа |
| **Avito** | [developers.avito.ru](https://developers.avito.ru/) → заявка на доступ к API | Messenger API + Avito Работа | по модерации, срок не публикуется |

### Что нужно от компании до подачи заявок

- [ ] **Аккаунт работодателя на hh.ru** с правами менеджера (кто именно — указать ФИО и e-mail)
- [ ] **Юридические данные** (наименование, ИНН) — их спрашивают при регистрации приложения
- [ ] **Аккаунт Avito для бизнеса** и подтверждённый профиль работодателя
- [ ] **Действующий тариф Talantix** и контакт администратора
- [ ] **Ответственный за обработку персональных данных** (152-ФЗ) — кто подпишет политику
- [ ] Решение: работаем на **российской LLM** или на зарубежной с обезличиванием

## 1. hh.ru — регистрация приложения

### Что сделать

1. Зайти на [dev.hh.ru/admin](https://dev.hh.ru/admin) **под аккаунтом работодателя**
   (не под личным аккаунтом соискателя — иначе приложение не получит доступ к откликам).
2. Создать приложение, указать:
   - **Название:** `AI-рекрутер` (или рабочее название продукта);
   - **Тип:** приложение работодателя;
   - **Redirect URI:** адрес, куда hh.ru вернёт код авторизации
     (например `https://<ваш-домен>/oauth/hh/callback`). Для локальной отладки
     можно указать `http://localhost:8000/oauth/hh/callback`;
   - **Описание сценария** (см. ниже).
3. Дождаться модерации (до 15 рабочих дней).
4. После одобрения получить `client_id` и `client_secret` → положить в `.env`
   (`HIREBOT_HH__CLIENT_ID`, `HIREBOT_HH__CLIENT_SECRET`).

### Текст описания для модерации

> Сервис автоматизирует первичную обработку входящих откликов на вакансии
> работодателя. Сотрудник компании авторизует приложение через OAuth и явно
> подтверждает подключение своего аккаунта. Далее приложение:
> получает список новых откликов по выбранным вакансиям, читает приложенные
> резюме, формирует для рекрутера предложения по уточняющим вопросам и
> приглашениям на собеседование и **отправляет их только после подтверждения
> рекрутером** (режим ручного подтверждения включён по умолчанию).
>
> Приложение не выполняет массовых рассылок, не отправляет сообщения без
> ведома и согласия авторизованного пользователя (п. 4.9 Условий использования
> API), не хранит логины и пароли пользователей (п. 3.6) — используется только
> OAuth-токен. Все автоматические действия фиксируются в неизменяемом журнале,
> доступном рекрутеру.

**Почему так.** В ходе исследования условий API найдены два пункта, которые
напрямую касаются нашего сценария и которые конкуренты игнорируют
(например, FriendWork требует вводить логин и пароль hh.ru, что нарушает п. 3.6):

- **п. 3.6** — запрещено хранить логины и пароли пользователей;
- **п. 4.9** — приложение не должно вызывать активные действия в API без ведома
  авторизуемых пользователей и без их согласия.

Наш ответ на это уже реализован в коде: только OAuth-токен, режим подтверждения
рекрутером (`HIREBOT_POLICY__REQUIRE_HUMAN_APPROVAL`), аудит всех автосообщений.

### Вопросы, которые стоит задать в заявке

1. Какой набор прав нужно отметить, чтобы читать **отклики** и **переписку** по вакансиям работодателя?
2. Доступен ли **Chats API** и **Webhook API** для нашего приложения? Если да — пришлите список событий и способ проверки подписи.
3. Есть ли численные лимиты запросов (`X-RateLimit-*`) и рекомендованный интервал поллинга?
4. Каков актуальный срок жизни access-токена и правила обновления?

> Эти четыре вопроса — не формальность: в публичной документации
> ([docs/research/hh-api.md](research/hh-api.md)) числовых лимитов нет, а перечень
> вебхук-событий не раскрыт. Ответы сэкономят недели догадок.

### Что уже известно и учтено в коде

| Особенность hh.ru | Как учтено |
|---|---|
| Только `authorization_code` (3-legged); `client_credentials` даёт 403 | реализован OAuth-флоу |
| Refresh-токен **одноразовый** и только после истечения | single-flight обновление через распределённую блокировку |
| Заголовок `HH-User-Agent` обязателен | задаётся централизованно |
| Лимит **5 сообщений подряд** | счётчик подряд идущих исходящих |
| `403` ≠ `404` ≠ `429` у резюме | разные ветки обработки |
| Пути действий нельзя хардкодить | действия берутся из `actions[]` ответа |

## 2. Talantix — токены и подтверждение тарифа

### Что нужно выяснить (это определяет объём работ)

Отправить администратору Talantix:

> Здравствуйте! Мы интегрируем нашу систему подбора с Talantix через API
> (`POST https://api.talantix.ru/graphql`). Подскажите, пожалуйста:
>
> 1. Доступен ли API на нашем текущем тарифе? Если нет — на каком тарифе он
>    открывается и что нужно для перехода?
> 2. Можете ли выдать API-токен (access + refresh) с правами на: чтение встреч
>    календаря, создание/изменение/удаление встреч, чтение вакансий и кандидатов,
>    чтение списка менеджеров?
> 3. Какой у вас лимит запросов и как считается сложность GraphQL-запроса
>    (в документации указано значение около 2500)?
> 4. Валидирует ли `createCalendarMeeting` пересечение с уже существующими
>    встречами? Если нет — мы будем проверять занятость на своей стороне.
> 5. Требуется ли оплаченное рабочее место менеджера для создания встречи?
> 6. Синхронизация с Google/Outlook — она двусторонняя? То есть появятся ли в
>    Talantix события, созданные нами напрямую в Google Calendar?
> 7. Сохраняются ли интеграции и токены при смене администратора?

### Процедура получения токена

1. **Администратор** компании входит в личный кабинет Talantix.
2. Раздел с API-токенами → выпустить пару **access + refresh**.
3. Передать токены нам (безопасным каналом, не в мессенджер).
4. Мы кладём их в `.env`: `HIREBOT_TALANTIX__ACCESS_TOKEN`, `HIREBOT_TALANTIX__REFRESH_TOKEN`.

### Важные ограничения (учтены в коде)

| Ограничение | Следствие |
|---|---|
| Access-токен ~24 часа, refresh ~120 дней, **ротация одноразовая** | параллельное обновление убивает сессию → single-flight блокировка |
| Вебхуков **нет** | только поллинг, интервал 5–15 минут |
| Окно чтения встреч **≤ 93 дней** | ограничение в конфиге, нарезка диапазона |
| **Free/busy-эндпоинта нет**, рабочих часов нет | сетку слотов строим сами |
| Синхронизация с Google/Outlook — **только наружу** | «напишем в Google — Talantix подхватит» **не работает** |
| Создание встречи, вероятно, **не валидирует конфликты** | проверяем занятость сами + блокировка слота в БД |
| Токены умирают при смене/блокировке администратора | нужен регламент: кто админ и что делать при смене |

> **Если API на тарифе недоступен** — это не остановка проекта. Календарный слой
> написан через порт `CalendarPort`, поэтому подключается альтернатива
> (Google Calendar / Microsoft Graph) без переделки воронки. Решение
> зафиксировано в [ARCHITECTURE.md](ARCHITECTURE.md), раздел 2.1.

## 3. Avito — заявка на доступ к API

### Что просим

Через [developers.avito.ru](https://developers.avito.ru/) — заявка на доступ к API:

> Просим предоставить доступ к API Avito для автоматизации работы с откликами
> на вакансии:
>
> 1. **Messenger API** — чтение и отправка сообщений в чатах по вакансиям.
> 2. **Avito Работа** — получение списка вакансий и входящих откликов,
>    чтение резюме откликнувшихся кандидатов.
> 3. **Webhooks** — подписка на события новых сообщений и откликов.
>
> Сценарий: работодатель публикует вакансии, кандидаты откликаются; наша
> система помогает рекрутеру быстро отвечать, задавать уточняющие вопросы и
> согласовывать время собеседования. Ответы кандидатам отправляются после
> подтверждения рекрутером.

### Вопросы, ответы на которые критичны

1. Доступен ли **Messenger API** для нашего аккаунта и на каких условиях?
2. Есть ли API для **получения откликов и резюме**? Если нет — какие официальные
   способы передачи откликов существуют (выгрузка, e-mail, интеграция с ATS)?
3. Есть ли **webhook**-подписка на новые сообщения и отклики?
4. Какие лимиты на отправку сообщений и запросы?
5. Нужен ли для доступа определённый тариф или партнёрский статус?
6. **Есть ли у Avito официальные партнёры-интеграторы** (ATS/HR-системы) с
   доступом к API, через которых можно получить доступ легально?

### Позиция по риску — фиксируем честно

**Парсинг и автоматизация интерфейса запрещены условиями Avito.** Санкции —
вплоть до блокировки аккаунта. Поэтому:

- продукт **не строится** на UI-автоматизации: в коде адаптера там, где контракт
  неизвестен, стоит явный `ChannelNotConfigured`, а не выдуманный endpoint;
- пока доступ не подтверждён, **Avito — это риск в плане проекта, а не функция**;
- обещать заказчику сбор откликов с Avito до получения доступа нельзя.

### План Б, если API не дадут

Продукт остаётся работоспособным на hh.ru, а для Avito возможны только
легальные варианты: официальная интеграция через партнёра, выгрузка откликов,
либо **полуавтоматический режим** — рекрутер получает подготовленный ответ и
отправляет его одним нажатием. Режим уже реализован в коде
(`HIREBOT_POLICY__REQUIRE_HUMAN_APPROVAL=true`).

## 4. Регламент работы с токенами (для эксплуатации)

Заполнить после получения доступов.

| Что | Кто отвечает | Что делать |
|---|---|---|
| Access-токен hh.ru истёк | | обновляется автоматически; при ошибке — переавторизация через OAuth |
| Refresh-токен hh.ru утерян/отозван | | повторный проход `authorization_code` |
| Токен Talantix отозван | | администратор выпускает новую пару |
| Сменился администратор Talantix | | перевыпустить токены **до** смены роли |
| Подозрение на утечку токена | | отозвать в личном кабинете, выпустить новый, проверить `audit_log` |

**Правила, которые не обсуждаются:**

- токены живут **только** в переменных окружения или секрет-хранилище, никогда — в git;
- логин и пароль пользователя не сохраняются **никогда** (запрещено условиями hh.ru);
- все автоматические сообщения кандидатам попадают в `audit_log`.

## 5. Что делать, пока доступов нет

Проект спроектирован так, чтобы работа не останавливалась:

| Направление | Статус |
|---|---|
| Воронка, скрининг, диалог, расписание, outbox | работает на тестовых двойниках, 305 тестов |
| `hirebot demo` | сквозной сценарий без ключей и сети |
| Измерение качества скрининга на эталонной выборке | в работе |
| Тесты устойчивости (таймауты, 429, дубли вебхуков) | в работе |
| UI рекрутера | запланировано |

**Что ускорит подключение площадок до минимума:** контрактный набор тестов для
адаптеров. После получения доступа подключение сведётся к тому, чтобы новый
адаптер прошёл уже написанный набор — а не к «написать интеграцию с нуля».
