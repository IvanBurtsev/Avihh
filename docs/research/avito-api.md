### 1.3 Точный флоу получения доступа

`[ФАКТ]` **Два механизма OAuth2** (`auth` spec, `components.securitySchemes`):

**A. `client_credentials` — «персональная авторизация»** (доступ к возможностям *своей* учётной записи):
1. «В личном кабинете получите `client_id` и `client_secret`.»
2. Отправить запрос к методу `token` с типом авторизации `client_credentials`.
3. Использовать `Authorization: Bearer <ACCESS_TOKEN>`.
4. **Токен живёт 24 часа** с момента получения.

**B. `authorization_code` — «авторизация других пользователей через приложение»:**
1. «**Зарегистрируйте приложение**» на <https://developers.avito.ru/applications>. Указать: имя приложения, **Redirect URI** (обязательно `https`, должен уметь принимать код), описание приложения.
2. Отправить пользователю ссылку:
   `https://avito.ru/oauth?response_type=code&pro_users_flow=true&client_id=<CLIENT_ID>&scope=messenger:read,messenger:write`
3. После одобрения Avito редиректит на Redirect URI с `?code=<AUTHORIZATION_CODE>`.
4. Обменять код: запрос к `token` с типом `authorization_code`, `client_id`, `client_secret`, `code`.
5. Получить `access_token` (**24 часа**) и `refresh_token` (**1 год**); обновление — тип `refresh_token`.

Источник: <https://github.com/MissiaL/avito-api/blob/main/references/sections/auth.md>.

`[ФАКТ]` **Точка получения токена:** `POST https://api.avito.ru/token` (в спеке `auth` три операции: `/token` — получение, `/token‎` — получение, `/token‎‎` — обновление; имена содержат невидимые символы — артефакт исходного спека, реальный путь — `/token`). `authorizationUrl` = `https://avito.ru/oauth`. Источник: <https://github.com/kozandlov/avito-python-sdk/blob/main/specs/raw/auth.json>.

`[ФАКТ]` `ClientCredentials` в спеке `job`/`messenger` имеет `tokenUrl: https://api.avito.ru/token` (в объединённом спеке отдельно зафиксировано `ClientCredentials__autoteka` → `https://pro.autoteka.ru/token`).

`[ФАКТ]` **Полный список scope** (из `auth.md`, дословно):
`autoload:reports`, `items:apply_vas`, `items:info`, `job:cv` (Получение информации резюме), `job:applications` (Получение информации об откликах на вакансии), `job:vacancy` (Работа с вакансиями), `job:write` (Изменение объявлений вертикали Работа), `messenger:read`, `messenger:write`, `short_term_rent:read`, `short_term_rent:write`, `stats:read`, `user:read`, `user_balance:read`, `user_operations:read`.

`[ВЫВОД]` Модерация/ревью приложения: `[ФАКТ]` п. 1.1 условий — «Вам предоставляется право доступа к публичному Авито API с момента **регистрации Приложения через службу поддержки** и получения API-Ключа». То есть в формулировке ToS регистрация идёт *через службу поддержки*, а не полностью автоматически. `[ВЫВОД]` Практически это означает ручной/полуручной шаг и возможный отказ — полноценной «самообслуживаемой» выдачи ключей для сторонних приложений в ToS не описано. Точную процедуру модерации подтвердить не удалось (страницы кабинета за WAF).

`[ФАКТ]` Контакты поддержки профессиональных инструментов: тел. **+7 495 777-10-66**, **supportautoload@avito.ru**; также 8 800 600-00-01 (с портала). Источники: `job.md`, Wayback-снимок страницы документации мессенджера.

## 2. MESSENGER API — конкретика

`[ФАКТ]` **Все пути (12 операций), verbatim из OpenAPI.** База: `https://api.avito.ru/`. Аутентификация: **`Authorization: Bearer <ACCESS_TOKEN>`**; допустимы **либо** `AuthorizationCode` (скоупы `messenger:read` / `messenger:write`), **либо** `ClientCredentials` (пустой список скоупов).

| Метод | Путь | Назначение | Требуемый скоуп |
|---|---|---|---|
| `GET` | `/messenger/v2/accounts/{user_id}/chats` | **Список чатов** | `messenger:read` |
| `GET` | `/messenger/v2/accounts/{user_id}/chats/{chat_id}` | Информация по чату | `messenger:read` |
| `GET` | `/messenger/v3/accounts/{user_id}/chats/{chat_id}/messages/` | **Список сообщений (V3)** | `messenger:read` |
| `POST` | `/messenger/v1/accounts/{user_id}/chats/{chat_id}/messages` | **Отправка сообщения** (текст) | `messenger:write` |
| `POST` | `/messenger/v1/accounts/{user_id}/chats/{chat_id}/messages/image` | Отправка сообщения с изображением | `messenger:write` |
| `POST` | `/messenger/v1/accounts/{user_id}/chats/{chat_id}/messages/{message_id}` | **Удаление** сообщения | `messenger:write` |
| `POST` | `/messenger/v1/accounts/{user_id}/chats/{chat_id}/read` | Отметить чат прочитанным | `messenger:read` |
| `POST` | `/messenger/v1/accounts/{user_id}/uploadImages` | Загрузка изображений (`multipart/form-data`) | `messenger:write` |
| `GET` | `/messenger/v1/accounts/{user_id}/getVoiceFiles` | **Получение голосовых сообщений** | `messenger:read` |
| `POST` | `/messenger/v2/accounts/{user_id}/blacklist` | Добавить пользователя в чёрный список | `messenger:write` |
| `POST` | `/messenger/v3/webhook` | **Включение webhook-уведомлений (V3)** | `messenger:read` |
| `POST` | `/messenger/v1/webhook/unsubscribe` | Отключение webhook-уведомлений | `messenger:read` |
| `POST` | `/messenger/v1/subscriptions` | **Получение списка подписок** (webhooks) | `messenger:read` |

Источник: <https://github.com/kozandlov/avito-python-sdk/blob/main/specs/raw/messenger.json> (дословный дамп `https://developers.avito.ru/web/1/openapi/info/messenger`).

### 2.1 Webhook — да, подписка есть

`[ФАКТ]` **Тело подписки:** `webhookSubscribeRequestBody` = `{"url": "<string>"}`, `url` — **required**. Используется и для `POST /messenger/v3/webhook`, и для `POST /messenger/v1/webhook/unsubscribe`.
`[ФАКТ]` **Ответ `POST /messenger/v3/webhook`:** `200` — успешный ответ; `201` — «**JSON сообщения, который будет приходить в webhook**» (т.е. в ответе отдаётся пример схемы).
`[ФАКТ]` **Требование к эндпоинту:** «После регистрации url'а для получения веб-хуков, убедитесь, что он доступен, работает и возвращает статус 200 ОК соблюдая **timeout 2s**, например, выполнив запрос: `curl --connect-timeout 2 <url-вашего-вебхука> -i -d '{}'`».

`[ФАКТ]` **Схема входящего webhook-сообщения `WebhookMessage`:**
- `id` (string) — ID сообщения
- `chat_id` (string) — ID чата
- `chat_type` (enum: `u2i` — чат по объявлению, `u2u` — чат по профилю, `a2u` — чат по профилю с Авито)
- `author_id` (integer) — ID отправителя
- `user_id` (integer) — «ID пользователя, получившего сообщение. Это **всегда аккаунт, на который зарегистрирован вебхук**»
- `item_id` (integer, nullable) — «ID объявления, актуально только для чатов с типом u2i»
- `type` (enum: `text`, `image`, `system`, `item`, `call`, `link`, `location`, `deleted`, `appCall`, `file`, `video`, `voice`)
- `content` (`MessageContent`)
- `created` (unix ts), `published_at` (RFC3339 UTC), `read` (unix ts, nullable)

### 2.2 Вложения: файлы и голос — ограниченно

`[ФАКТ]` **Голосовые: только чтение.** `GET /messenger/v1/accounts/{user_id}/getVoiceFiles` → схема `VoiceFiles` = `{"voices_urls": {"<ключ>": "<uri>"}}`.
`[ФАКТ]` **Изображения: чтение и отправка.** Входящие — через `MessageContent.image.sizes` (словарь `"ШxВ"` → URL). Исходящие — `POST .../uploadImages` + `POST .../messages/image`.
`[ФАКТ]` **Файлы и видео — НЕ поддерживаются.** Дословно из описания схемы `MessageContent`: «Для сообщений типов `"appCall"` `"file"` `"video"` возвращается **empty object (данные типы не поддерживаются)**».
`[ВЫВОД]` Итого по вложениям: можно читать текст, картинки, ссылки, локации, item-карточки, системные сообщения и голосовые (по URL); можно отправлять только **текст и изображения**. Отправка голосовых, документов и видео через API недоступна.

`[ФАКТ]` **Ограничение длины исходящего текста:** `sendMessageRequestBody.message.text` — «Текст сообщения (**максимум 1000 символов**)», `maxLength: 1000`; `type` — enum только `["text"]`.
`[ВЫВОД]` Курьёз: в `sendMessageRequestBody` в `required` указано `["url"]` — явная опечатка исходного спека (у тела отправки сообщения нет поля `url`). Не следует воспринимать как требование.

### 2.3 Rate limits

`[ФАКТ]` Спека `messenger` **не публикует числовое значение лимита**. Задокументированы только заголовки ответа: `X-RateLimit-Limit` — «Количество запросов в минуту», `X-RateLimit-Remaining` — «Доступное количество запросов в текущем временном окне».
`[ФАКТ]` **Для раздела `job` числовой лимит опубликован явно: «Базовое ограничение на число запросов — 10 rps»**, при превышении — HTTP `429` + те же заголовки `X-RateLimit-Limit` / `X-RateLimit-Remaining`. «Для изменения установленного лимита обратитесь в службу поддержки».
`[ВЫВОД]` Разумно проектировать интеграцию исходя из ~10 rps как общего базового лимита Avito Business API, но для мессенджера это **не подтверждено** — читайте `X-RateLimit-Limit` из ответов и адаптируйтесь.

### 2.4 Ограничения по иерархии аккаунтов (важно для продукта)

`[ФАКТ]` Из `messenger.md`, раздел «Работа с Иерархией Аккаунтов»:
- «Методы API работают **только для основного аккаунта компании**. Для работы с чатами компании нужно использовать **ключ авторизации компании**.»
- При ключе сотрудника список чатов «не будет возвращать чаты по объявлениям, где пользователь является привязанным сотрудником, а не автором объявления».
- **Ошибку вернут** при ключе сотрудника: просмотр чата/сообщений, отправка/удаление/прочтение, чёрный список, отправка изображений, получение/загрузка голосовых.

`[ФАКТ]` Сообщения чат-ботов Avito доступны для чтения; отличаются по `type = "system"` и заполненному `flow_id` (ID чат-бота). Примеры ID: `seller_audience_discount`, `sbc_seller_notification`, `flower_161071`.

`[ФАКТ]` «`GET /messenger/v3/.../messages/` — **Не помечает чат прочитанным**. После успешного получения списка сообщений необходимо вызвать метод `chatRead`. Для получения новых сообщений в реальном времени используйте webhooks.»

### 3.1 Как приходят отклики — webhook (рекомендуемый путь) и cron

`[ФАКТ]` Дословно: «**Работа с откликами через обратный вызов (webhook)** … Webhook (*Предпочтительный способ интеграции*)».

**Алгоритм (дословно, `job.md`):**
1. Реализовать POST-метод, который:
   - принимает тело `{"applyId": "623850d1d3819d935dd02702"}`, где `applyId` — идентификатор отклика;
   - поддерживает заголовок **`X-Secret`** для проверки подлинности источника;
   - «проверьте доступность метода, перед сохранением Webhook'а на него уйдет **POST-запрос с пустым body**, а в заголовке передадим `X-Secret`. В ответ ожидается код ответа `2**` в течение **двух секунд**».
2. Авторизация → токен.
3. `PUT /job/v1/applications/webhook` — `url` вашего POST-метода + `secret` (строка **максимум 100 символов**, передаётся в заголовке `X-Secret`). Метод создания проверит доступность вашего URL.
4. `GET` список вакансий через `item` API с `category=111` (111 — категория вакансии).
5. `POST /job/v1/applications/get_by_ids` — передать `applyId` в `ids`, **не больше 100 откликов за раз**.

**Доставка уведомлений (дословно):**
- «Вызов Webhook'а происходит **при создании отклика и при каждом обновлении его данных** — например, когда кандидат прошел чат-бота, когда обновились данные анкеты или резюме. По одному отклику может прийти **несколько уведомлений**, поэтому обеспечьте на своей стороне **проверку уникальности по идентификатору отклика**.»
- «Успешной доставкой считается код ответа `2**`. **Таймаут одного запроса — 3 секунды**, поэтому рекомендуем сразу возвращать `2**`, а обработку выполнять асинхронно.»
- «Если ваш метод ответил ошибкой или не ответил, уведомление будет переотправлено с увеличивающимися интервалами — через **1, 2, 3, 4, 5, 10, 30 минут, далее раз в час**. Общее время попыток — **около 31 часа**, после этого уведомление не доставляется.»
- «Если в течение **10 дней** не будет ни одного успешного вызова, **подписка деактивируется**, о чем мы сообщим письмом. Чтобы возобновить получение уведомлений, зарегистрируйте Webhook заново.»

**Альтернатива — cron-опрос (дословно):** шаги: авторизация → список вакансий (`category=111`) → `applicationsGetByIds` c `vacancyIds`, `updatedAtFrom=<YYYY-MM-DD>`, `cursor`, `is_viewed`. Пагинация: «ограничение на количество откликов в одном ответе **100 штук**», `cursor` = `id` последнего элемента массива `applies`. «Настройте расписание запуска алгоритма по вашим требованиям, но **не чаще чем один раз в 5 минут**. Для более оперативного получения откликов используйте webHook.»

`[ФАКТ]` **Особенность с чат-ботом:** «Если соискатель откликнулся на вакансию в которой есть чат-бот, то в список откликов и в webhook он попадет **только после его прохождения или же по истечению времени прохождения опроса (1 час)**.» Результат опроса — в поле `prevalidation` (`status`: `not_complete`/`success`/`failed`, `summary` — пары «вопрос → ответ»).

### 3.2 Что реально содержится в отклике

`[ФАКТ]` Поля из `get_by_ids` (дословно, `job.md`):
- `applicant.data` — информация о кандидате, заполненная им о себе
- `contacts.chat` — **идентификатор чата** (можно открыть чат через Messenger API); «если способ связи только звонок, то chat будет пустым»
- `contacts.phones` — номер телефона соискателя в формате `72002000014`; «кандидат может отказаться от передачи номера телефона»
- `employee_id` — сотрудник, если вакансия опубликована «от имени» сотрудника
- `type` — `by_chat` (кандидат откликнулся) или `by_phone` (просмотрел номер из вакансии)
- `vacancy_id` — ID вакансии
- `is_viewed` — просмотрен ли отклик
- `prevalidation` — результат чат-бота
- `enriched_properties` — собранные данные кандидата: `status`, `citizenship` (гражданство), `experience`, `phone`, `gender`, `full_name`

`[ФАКТ]` **Связка с чатом:** в `job.md` поле `contacts.chat` прямо ссылается на «просмотр содержимого чата» в разделе messenger. `[ВЫВОД]` Это и есть официальный способ «собрать отклик → открыть чат → ответить»: отклик даёт `applyId` и `contacts.chat`, далее Messenger API даёт `chat_id`, историю и отправку.

### 3.3 Чего в API НЕТ (честный список)

`[ФАКТ]` / `[ВЫВОД]`:
- **Нет отправки сообщения соискателю «в отклик» отдельным методом** — переписка идёт через Messenger API по `chat_id` из `contacts.chat`. `[ВЫВОД]` Если `contacts.chat` пуст (связь только по звонку), писать в чат из API некуда.
- **Нет webhook на «новое резюме в поиске»** — webhook раздела `job` работает **только по откликам** (`applications/webhook`). Поиск резюме — только активный `GET /job/v1/resumes/`. `[ВЫВОД]`
- **Нет пуш-уведомлений о новых сообщениях в чате вне Messenger webhook** — используйте `POST /messenger/v3/webhook`. `[ФАКТ]`
- **Нет API для чтения «откликов» по резюме-сторонней логики (массовые приглашения)** — в спеке нет метода приглашения/оффера. `[ВЫВОД]` Набор действий по отклику ограничен: `set_is_viewed` и `apply_actions` (батч-смена статуса); конкретный список доступных статусов даёт `get_states`.
- **Отправка файлов/видео в чат недоступна** (см. §2.2). `[ФАКТ]`
- **Публикация вакансий без платного тарифа невозможна** (нужен пакет размещения; `billing_type` принимает только `package`; `packageOrSingle` и `single` — «выведены из эксплуатации»). `[ФАКТ]`
- **Контакты резюме списывают платный лимит** — чтение резюме как таковое отделено от доступа к контактам (`/contacts/`). `[ФАКТ]`

`[ФАКТ]` Ещё одно ограничение: «При передаче заголовка `X-Employee-Of` на сотрудника распространяется тариф компании»; управление лимитами сотрудников — на <https://www.avito.ru/employees>.

Это challenge-механизм: клиент обязан вычислить ответ и повторить запрос. `[ВЫВОД]` Классическая защита от headless-ботов, требующая исполнения JS.
2. **WAF с блокировкой по IP.** `https://developers.avito.ru/api-catalog` → `HTTP 429`, страница `Доступ ограничен: проблема с IP` (вёрстка `firewall__header`, `firewall__container`, `firewall__content`). Т.е. датацентровые/зарубежные IP блокируются на уровне WAF до какой-либо логики приложения.
3. **Блокировка краулера Internet Archive.** В CDX-индексе Wayback для `https://www.avito.ru/legal/` множество снимков сохранено со статусом **429** (например, серия 05–27.02.2022, `20220205120050` → 429, `20220218062817` → 200, `20220227040129` → 429).
4. **reCAPTCHA включена** в веб-приложении Avito: в `window.__initialData__` на страницах Avito присутствует тоггл `"recaptcha_enabled": true` (наряду с `securedtouch: true`). Источник: сохранённый HTML страницы документации мессенджера (Wayback), скрипт `window.__initialData__`.
5. **Публикуемые серверные лимиты.** `429` + `X-RateLimit-Limit` / `X-RateLimit-Remaining` для API; базово 10 rps в разделе `job`; лимит длины сообщения 1000 символов.

`[ВЫВОД]` (не подтверждено источником, помечаю явно): про **device fingerprint** и **лимиты на количество исходящих сообщений в чате** прямых доказательств я не нашёл — в спеке Messenger лимит сообщений не описан. Наличие `securedtouch: true` и reCAPTCHA косвенно указывает на поведенческий/устройство-зависимый скоринг, но конкретики (сколько сообщений в час, какие сигналы) публично нет. Считать это гипотезой.

`[ФАКТ]` Дополнительное подтверждение жёсткости антибота — от независимого разработчика, который ведёт выгрузку каталога: «Антибот отвечает HTTP 429 на curl и headless-браузер. Выгружай из обычного браузера с пройденной проверкой». Источник: <https://github.com/MissiaL/avito-api/blob/main/references/sources.md>.

## 6. Альтернативные легальные пути

### 6.1 Официальные SDK от Avito — только для Рекламы

`[ФАКТ]` У `avito-tech` на GitHub есть официальные SDK, но **исключительно для Авито Рекламы (Ads)**: `avito-ads-sdk-python3`, `avito-ads-sdk-go`, `avito-ads-sdk-typescript`, `avito-ads-sdk-php`. Проверено через GitHub API: <https://api.github.com/orgs/avito-tech/repos?per_page=100>. Последние коммиты всех четырёх — 08.06.2026.
`[ФАКТ]` Прямая цитата из независимого справочника: «SDK **не заменяют** полный каталог Business API и **не служат источником схем для Messenger, Promo или Автозагрузки**». Источник: <https://github.com/MissiaL/avito-api/blob/main/references/sources.md>.

`[ВЫВОД]` **Официальных SDK для Messenger / Работы / Автозагрузки от Avito не существует.** Все SDK на GitHub — сторонние (`kozandlov/avito-python-sdk`, `18studio/avito_python_api`, `progdog-ru/avito-rest-api-php`, `zlexdev/avitoapi`, `kmlebedev/avito-gen-api` и др.). Это значит: код интеграции придётся писать/поддерживать самим.

### 6.2 Партнёрские интеграции HR-систем (Talantix / Huntflow / Skillaz и др.)

`[НЕ ПРОВЕРЕНО]` **Официального подтверждения партнёрства Avito с Talantix/Huntflow/Skillaz получить не удалось** — ни в открытых спеках, ни в доступных страницах помощи (support.avito.ru отдаётся как SPA и в Wayback не сохранил正文). Я **не утверждаю** наличие таких партнёрств.

`[ВЫВОД]` Однако архитектурно понятно, что «интегратор» здесь не нужен как посредник: официальный API **уже** даёт и отклики, и резюме, и чат — но требует **Максимальную подписку на аккаунте работодателя** и регистрацию приложения. То есть путь «через партнёра» не даёт доступа к данным, которых нет в публичном API; он может дать только готовую обвязку и, возможно, обход требования собственной регистрации приложения.

`[ФАКТ]` Что действительно существует и подтверждено: у Avito есть **Иерархия Аккаунтов** (`accounts-hierarchy`) и заголовок `X-Employee-Of` / `X-Is-Employee`, позволяющие работать от имени сотрудников компании с тарифом компании. Это официальный механизм для агентств/HR-команд, а не партнёрская программа.

### 6.3 Парсинг email-уведомлений

`[ВЫВОД]` **Не рекомендую как основной канал.** Причины: (а) уведомления Avito о новых откликах/сообщениях приходят на почту аккаунта, но состав и формат писем не являются контрактным API и меняются без уведомления; (б) письма содержат неполные данные (нет полного резюме, часто нет `chat_id`); (в) чтобы «ответить в чат», всё равно нужен Messenger API или UI. Может работать как **дешёвый триггер** («появился отклик → дёрнуть `get_by_ids`»), но это не заменяет webhook и создаёт задержку.

### 6.4 Браузерная автоматизация (Playwright) — риски и меры

`[ФАКТ]` Технические препятствия, подтверждённые наблюдением: PoW-challenge (HTTP 439), WAF-блок по IP (HTTP 429), включённая reCAPTCHA, `securedtouch`.
`[ФАКТ]` Мнение независимого практика: headless-браузер получает 429, нужен «обычный браузер с пройденной проверкой».

`[ВЫВОД]` Риски UI-автоматизации, по убыванию:
1. **Блокировка аккаунта работодателя** — самый дорогой риск: это аккаунт клиента с оплаченным тарифом и историей. Санкция прямо предусмотрена п. 1.5 API-ToS («нарушения, приведшие к блокировке профиля пользователя») и, по общему соглашению Avito, — за автоматизированный доступ/обход ограничений.
2. **Юридический/договорный риск** — п. 2.2 ограничивает применение API базой объявлений пользователя; парсинг чужих данных и обход защиты выходят за рамки.
3. **Хрупкость** — смена вёрстки, `data-marker`-атрибутов, появление капчи, PoW-ротация ломают селекторы и пайплайн без предупреждения.
4. **Нестабильность сессии** — device fingerprint, привязка к устройству, 2FA/подтверждение входа.

`[ВЫВОД]` Меры снижения (не устраняют риск, только уменьшают вероятность детекта): выделенный стабильный IP в РФ (резидентный, не датацентровый); постоянный профиль браузера (persistent context) с сохранением cookies/localStorage; реальный headful-браузер вместо headless; человекоподобные задержки и ограничение частоты действий; ручное прохождение капчи/PoW при первом входе; отсутствие параллельных сессий; обязательное согласие клиента в письменном виде. **Все эти меры — обход защиты, и это осознанное решение с принятием риска блокировки, а не «безопасный» путь.**

## 7. Практический вердикт

### 7.1 Что официально возможно уже сегодня

`[ФАКТ]` Для аккаунта работодателя с **Максимальной подпиской** в Работе (и/или Мессенджере) и зарегистрированным приложением:

1. **Сбор свежих откликов** — `PUT /job/v1/applications/webhook` (мгновенно, с `X-Secret`) или cron-опрос `POST /job/v1/applications/get_by_ids` не чаще 1 раза в 5 минут, по 100 откликов.
2. **Полные данные отклика** — `POST /job/v1/applications/get_by_ids`: анкета кандидата, телефон, `chat_id`, результаты чат-бота, `enriched_properties`.
3. **Резюме** — `GET /job/v1/resumes/` (поиск), `GET /job/v2/resumes/{resume_id}`, `GET /job/v1/resumes/{resume_id}/contacts/` (контакты — с платным списанием лимита).
4. **Открыть чат и ответить** — `GET /messenger/v2/accounts/{user_id}/chats`, `GET /messenger/v3/accounts/{user_id}/chats/{chat_id}/messages/`, `POST /messenger/v1/accounts/{user_id}/chats/{chat_id}/messages` (текст до 1000 символов), `.../read` для отметки прочтения, webhook `POST /messenger/v3/webhook` для новых сообщений.
5. **Публикация/редактирование вакансий** — `POST /job/v2/vacancies` и др. (требует оплаченного тарифа на размещение).
6. **Автозагрузка** — XML-фид + `POST /autoload/v1/upload`, отчёты v4.

### 7.2 Что требует партнёрства / тарифа / согласований

`[ФАКТ]`/`[ВЫВОД]`:
- **Максимальная подписка** на аккаунте работодателя — жёсткое условие (иначе `402` для job и недоступность Messenger API в Работе).
- **Регистрация приложения** — по ToS «через службу поддержки»; `[ВЫВОД]` вероятен ручной шаг/ревью.
- **Согласие пользователя** на `authorization_code` со скоупами `job:applications`, `job:cv`, `messenger:read`, `messenger:write` — для мультиаккаунтной модели (агентство/сервис).
- **Оплата размещения вакансий** и **покупка контактов резюме** — отдельные платные действия.
- **Партнёрство с Avito** для доступа к данным, которых нет в публичном API (например, к чужим базам резюме вне поиска) — `[ВЫВОД]` публичных свидетельств такой программы для HR-вертикали я не нашёл; официальный API и есть «партнёрский» контур.

### 7.3 Что остаётся только UI-автоматизации

`[ВЫВОД]` Практически **ничего критичного** — это главный вывод исследования. Полный целевой сценарий («собрать свежие отклики + открыть чат + ответить») **покрывается официальным API**. UI-автоматизация нужна только для:
- аккаунтов **без** Максимальной подписки (там API отдаёт `402`) — то есть автоматизация здесь = способ обойти платный барьер, что прямо повышает риск блокировки;
- действий, которых в API нет: отправка **файлов/видео/голосовых** в чат, массовые приглашения, работа с разделами вне API;
- если клиент не готов регистрировать приложение и проходить `authorization_code`.

`[ВЫВОД]` **Рекомендация:** строить продукт на официальном API (`job` + `messenger`), позиционируя его как «подключите свой аккаунт Avito с Максимальной подпиской». Это единственный путь, который (а) не нарушает п. 2.2/2.7 условий, (б) не создаёт риска блокировки аккаунта клиента, (в) устойчив к изменениям вёрстки. UI-автоматизацию рассматривать только как явно обозначенный «legacy/fallback» режим для аккаунтов без подписки — с письменным принятием риска клиентом, выделенным РФ-IP и постоянным профилем браузера, и с пониманием, что это обход защиты.

### 7.4 Открытые вопросы, требующие проверки на живом доступе

1. Точные числовые лимиты Messenger API (в спеке только заголовки).
2. Полный список статусов откликов (`get_states`) и допустимых значений `apply_actions`.
3. Действующая процедура регистрации приложения (портал за WAF) — автоматическая или через поддержку.
4. Есть ли ограничения на количество webhook-подписок на приложение.
5. Актуальность снимка спека от 03.10.2026 (проверить `changelog` каждого раздела).
6. Наличие партнёрской программы Avito для HR-систем.
