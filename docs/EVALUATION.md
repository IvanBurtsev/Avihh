# Оценка качества скрининга

> Документ закрывает ограничение из [ARCHITECTURE.md](ARCHITECTURE.md): «точность
> промптов не измерена на размеченной выборке». Здесь есть выборка, метрики и
> разбор ошибок. Но это **замер harness на fake-провайдере**, а не точность
> продукта на реальной LLM: цифры ниже — нижняя граница и проверка того, что
> сам механизм замера и правила вердикта работают.

## 1. Что именно измеряется

Замер идёт через настоящий `ScreeningService.screen`, а не через прямой вызов
`LlmPort`. Это принципиально: сервис

* применяет quality-gate: пустой/почти пустой текст → `NEEDS_REVIEW` **до**
  вызова модели;
* пересчитывает балл по весам критериев **на нашей стороне**;
* применяет `policy.min_score_to_invite` (по умолчанию 70);
* применяет правила вердикта v2 (см. ниже);
* проверяет критерии на защищённые признаки через `PolicyGuard`;
* сохраняет результат в репозиторий и кэширует по хэшу резюме.

Если мерить «сырой» ответ модели, можно получить красивые цифры у компонента,
который в продукте не принимает решение. Поэтому замер повторяет продуктовый
путь целиком.

### Правила вердикта v2

| Условие | Вердикт |
|---|---|
| Хотя бы один обязательный критерий провален | `weak`, балл не выше **40** (`MUST_HAVE_SCORE_CAP`) |
| Балл ≥ 93, все обязательные ≥ 85, ни один критерий не ниже 60 и не помечен пробелом | `strong_match` |
| Балл ≥ 70, но условия «силы» не выполнены | `match` |
| 55 < балл < 70 | `weak` — решает человек |
| Балл ≤ 55 | `reject` |

Порог `strong_match` поднят с 85 до 93 (`STRONG_MATCH_MARGIN` 15 → 23) и
дополнен двумя условиями: обязательные критерии должны быть закрыты с оценкой
≥ 85, а «заметных пробелов» (критерий ниже 60 или `is_gap`) быть не должно.
Иначе уверенный middle с 4–6 годами получал `strong_match` на ровном месте.

### Quality-gate

До вызова модели считается число **содержательных** символов (буквы и цифры,
без пробелов и пунктуации). Если их меньше **60**, возвращается несохранённый
`NEEDS_REVIEW` с причиной, все критерии помечены проваленными, модель **не
вызывается**. Это одновременно экономия денег и защита от «изобретённого»
балла на мусорном тексте.

### Две плоскости метрик

| Плоскость | Что показывает | Зачем нужна |
|---|---|---|
| **Бинарное решение** «приглашать / не приглашать» | precision, recall, F1, accuracy, specificity | Это бизнес-эффект: ложное приглашение тратит время рекрутера и кандидата, ложный отказ теряет человека |
| **Точность вердикта** | доля случаев, где `actual_verdict == expected_verdict` | Диагностика: где расходятся правила вердикта и человеческая оценка |
| **Точность по must-have** | доля случаев, где набор проваленных обязательных критериев совпал с разметкой | Диагностика: умеет ли модель находить именно обязательные пробелы, а не «средний балл» |

Бинарное решение выводится из вердикта: приглашение — это `strong_match` или
`match`. `weak`, `needs_review` и `reject` — **не** автоматическое приглашение;
`weak` и `needs_review` уходят человеку.

### Какой fake-провайдер мерится

До правок harness по умолчанию собирал **тестовую** заглушку из
`hirebot.testing.fakes`, у которой своя, исторически разошедшаяся эвристика.
Продуктовый `provider=fake` использует
[`adapters/llm/fake.py`](../src/hirebot/adapters/llm/fake.py). Теперь
`run_evaluation` по умолчанию подставляет именно продуктовый адаптер
(`fake-llm-v2`), иначе цифры отчёта относились бы к коду, которого нет в
продуктовой сборке. Тестовая заглушка осталась для тестов сервисов, а подмена
реальной LLM — через `container_factory`.

## 2. Эталонная выборка

Файл: [`data/evaluation/golden_set.json`](../data/evaluation/golden_set.json),
версия `1.1.0`, **25 случаев**. Вакансия — Python-разработчик (middle), 5 критериев:

| Ключ | Критерий | Вес | Must-have |
|---|---|---|---|
| `python` | Коммерческая разработка на Python, не менее 3 лет | 3.0 | да |
| `sql` | Реляционные БД и SQL, PostgreSQL | 2.0 | да |
| `api` | Проектирование REST API | 2.0 | нет |
| `docker` | Docker и контейнеризация | 1.0 | нет |
| `english` | Английский для документации, не ниже B1 | 1.0 | нет |

Разметка (`expected_verdict`, `expected_should_invite`,
`expected_must_have_gaps`) выставлена по смыслу резюме относительно критериев,
а не по выводу fake-модели. `notes` в JSON объясняет каждое решение;
`expected_should_invite` согласован с вердиктом.

Покрытые сценарии:

* явное сильное соответствие (`strong-full-match`);
* провал must-have при высоком среднем балле (`must-have-gap-high-average`);
* пограничный случай около порога (`borderline-near-threshold`);
* junior с потенциалом (`junior-potential`);
* смена профессии: курсы и учебные проекты вместо коммерческого опыта
  (`career-change-courses`);
* overqualified (`overqualified`);
* практически пустое резюме (`practically-empty-resume`);
* попытка инъекции промпта (`prompt-injection`);
* пол и возраст в резюме — три версии одного профиля
  (`gender-neutral-baseline`, `gender-male-age`, `gender-female-age`);
* резюме на английском (`english-language-resume`);
* опечатки в названиях технологий (`typos-russian`);
* очень короткое резюме (`short-resume`);
* непрофильный опыт — продажи (`unrelated-sales-experience`);
* аналитик с Python и SQL, но без backend (`data-analyst-python-sql`);
* **новые случаи под исправленные проблемы**:
  * возраст при небольшом опыте (`age-small-experience`);
  * возраст при пограничном стаже (`age-borderline-experience`) — пара к
    `gender-neutral-baseline` для проверки утечки;
  * преподавание как основной «опыт» по навыку (`teaching-python-only`);
  * английское резюме без SQL (`english-resume-sql-gap`);
  * явная привязка стажа к навыку (`python-years-explicit`);
  * упоминание навыков без стажа (`python-mentioned-without-years`);
  * сильный общий стаж без обязательного навыка (`senior-total-years-no-sql`);
  * почти пустое резюме (`almost-empty-resume`);
  * опечатки и разрядка «Postgre SQL», «Fast Api» (`typos-postgre-fastapi`).

Загрузчик (`load_dataset`) строгий: дубли `id`, неизвестный вердикт, пустые
критерии и ссылка на несуществующий ключ в `expected_must_have_gaps` — ошибка
выборки. Это защищает от «зелёных» метрик, посчитанных по испорченным данным.

## 3. Как воспроизвести

```powershell
# CLI-отчёт (публичный путь, используется в CI)
.venv\Scripts\hirebot.exe evaluate

# Тесты подсистемы
.venv\Scripts\python.exe -m pytest tests/unit/adapters tests/unit/evaluation -o addopts= -q

# Линтер и типы
.venv\Scripts\python.exe -m ruff check src/hirebot/adapters src/hirebot/services/screening.py src/hirebot/evaluation
.venv\Scripts\python.exe -m mypy src/hirebot/adapters
```

Прогон из Python (то же, что делает CLI):

```python
import asyncio

from hirebot.evaluation import load_dataset, run_evaluation


async def main() -> None:
    dataset = load_dataset("data/evaluation/golden_set.json")
    report = await run_evaluation(dataset)
    metrics = report.decision_metrics
    print(
        f"cases={len(report.outcomes)} model={report.model} "
        f"precision={metrics.precision:.3f} recall={metrics.recall:.3f} "
        f"f1={metrics.f1:.3f} verdict_accuracy={report.verdict_accuracy:.3f} "
        f"must_have_accuracy={report.must_have_accuracy:.3f}"
    )


asyncio.run(main())
```

### Подстановка реальной модели

`run_evaluation` принимает `container_factory`. Фабрика должна вернуть
контейнер с тем же диалогом, вакансией и резюме, но с другим `LlmPort`:

```python
from hirebot.evaluation import build_case_container


async def factory(dataset, case):
    return await build_case_container(dataset, case, llm=real_llm)


report = await run_evaluation(dataset, container_factory=factory)
```

`build_case_container` наполняет fake-контейнер данными случая и подменяет
только `llm`; остальной harness (quality-gate, пересчёт балла, порог,
must-have, политика) не меняется. Соглашение: фабрика создаёт диалог с внешним
id `case_conversation_external_id(case.id)`; `build_case_container` делает это
сам. Порог можно изменить через `settings=...` — это часть проверяемой
политики, а не константа замера.

Прогоны без сети и ключей. «До» в средней колонке — **честное сравнение на том
же наборе 1.1.0**: старый продуктовый fake (`fake-llm-v1`) подключён к тому же
harness до правок эвристики, правил вердикта и quality-gate. «После» — тот же
набор и тот же путь через `ScreeningService`.

## 5. Разбор: какие проблемы закрыты

### 5.1. Ложное приглашение: преподавание и курсы (было FP)

`career-change-courses`: было `match` с 84.6 и без must-have-пробелов, стало
`weak` с 40 и пробелом `python`. `teaching-python-only` — аналогично. Причина
исправления не «подгонка под случай», а общее правило fake-модели:

* стаж берётся только из конструкций опыта, а не из любого «N лет»;
* у каждой строки резюме определяется тип доказательства: **коммерческое**,
  **учебное** (курсы, школа, вуз, стажировка, преподавание, pet-проекты) или
  **упоминание**;
* для критерия «не менее N лет коммерческой разработки» учебное доказательство
  даёт 45 баллов (пробел), а не закрывает критерий;
* SQL/PostgreSQL при этом остаются подтверждёнными учебными проектами (65
  баллов), потому что критерий SQL не требует коммерческого стажа. Поэтому у
  `career-change-courses` пробел только `python`.

### 5.2. Ложный отказ: английское резюме (было FN)

`english-language-resume`: было `weak` с 40 и пробелами `python`, `sql`, стало
`strong_match` с 93.8 без пробелов. Словарь навыков расширен английскими
формами и смешанными записями: `PostgreSQL databases` → SQL, `English (C1)` →
английский C1, `6 years of commercial software development` → общий стаж,
`Built ... in Python` → коммерческое подтверждение Python. Опечатки и разрядка
(«Postgre SQL», «Fast Api», «Pythom», «Pyhton») распознаются отдельным
допуском, а не считаются другой технологией.

`typos-russian` и `python-years-explicit` — та же причина: раньше любая
нестандартная запись давала must-have-пробел и потолок 40.

### 5.3. Утечка по возрасту

До правок `gender-male-age` и `gender-female-age` получали `strong_match`
(85.2/85.3), а `gender-neutral-baseline` — `match` (84.9): добавленная строка
«Мужчина, 34 года» меняла вердикт. После правок все три версии дают **91.3 и
`match`**; `age-small-experience` и `age-borderline-experience` обрабатываются
одинаково с версиями без возраста. Общие правила:

* «34 года», «возраст 34», «1989 г.р.» не участвуют в извлечении стажа;
* возраст/пол/гражданство не попадают ни в один критерий и не влияют на балл;
* из scoring убран детерминированный «jitter» от хэша текста: он давал разным
  версиям одного профиля разные баллы, хотя различались только защищённые
  строки.

### 5.4. Калибровка `strong_match` (было 85+)

Порог «сильного» вердикта поднят до 93 и дополнен условиями: все обязательные
критерии ≥ 85 и ни одного заметного пробела. Результат: `overqualified` и
`age-borderline-experience` стали `match`, `typos-russian` — `match`; при этом
`strong-full-match` остался `strong_match`. Точность вердикта выросла с 0.320
до 0.880 на одном и том же наборе.

### 5.5. Пустые и короткие резюме

`practically-empty-resume`, `short-resume` и `almost-empty-resume` теперь
получают `needs_review` **без вызова модели**: 34, 18 и 20 содержательных
символов из 60 минимальных. Тест
`tests/unit/evaluation/test_quality_gate.py` проверяет по счётчику
`FakeLlmAdapter.screen_calls`, что для этих случаев вызовов **ноль**, а для
остальных — ровно один. В результате нет ни «изобретённого» балла, ни трат на
мусор.

### 5.6. Провал обязательного критерия

Жёсткий потолок сохранён: `must-have-gap-high-average` и
`senior-total-years-no-sql` дают 40 и `weak`, несмотря на сильный общий профиль.
Правило harness не изменилось — изменилась доказательная база модели, которая
теперь честно помечает пробел.

### 5.7. Инъекция промпта

`prompt-injection` остаётся без приглашения (`weak`, 15.0, оба must-have-пробела).
Harness не берёт балл из ответа модели, а fake-модель по построению не выполняет
инструкции из текста. Это регрессионный тест harness, а не тест устойчивости
реальной LLM.

### 5.8. Промпт v2 и валидация evidence

В [`prompts.py`](../src/hirebot/adapters/llm/prompts.py) поднят `PROMPT_VERSION`
до `v2`. Системный промпт теперь явно требует: дословный `evidence` по каждому
критерию; различение общего стажа и стажа по навыку; отделение коммерческого
опыта от курсов, учебных и pet-проектов, преподавания и стажировки; распознавание
навыков независимо от языка и формы записи; игнорирование защищённых признаков
(возраст и год рождения — не опыт); усиленную защиту от prompt injection.

`OpenAiCompatAdapter` дополнительно отбрасывает evidence, в котором нет ни одного
значимого слова из резюме: выдуманная цитата не зачитывает критерий (оценка ≤ 30,
`is_gap=True`). Это проверено тестами
[`test_llm_adapter.py`](../tests/unit/adapters/test_llm_adapter.py).

## 6. Что осталось и чего эти цифры не означают

### 6.1. Оставшиеся расхождения вердикта (3 из 25)

* **`english-language-resume`: ожидался `match`, получен `strong_match`
  (93.8).** Бинарное решение верное (приглашение есть). Причина в одном общем
  пороге: резюме с C1 и полным стеком набирает чуть больше 93, а
  `strong-full-match` — 93.2. Поднять порог нельзя, не потеряв единственный
  обоснованный `strong_match`; понижать оценку за «слишком хороший английский»
  неверно. Это ограничение калибровки по одному числу, а не ошибка бизнес-решения.
* **`prompt-injection` и `unrelated-sales-experience`: ожидался `reject`,
  получен `weak`.** Бинарное решение верное (не приглашаем). Политика продукта:
  при провале must-have вердикт не выше `weak` — судьбу человека решает человек,
  автоотказ выключен. Это осознанное поведение, зафиксированное тестом
  `test_must_have_gap_caps_score_and_verdict`.
* **`overqualified` теперь `match` — совпало с разметкой, но по другой
  причине.** Раньше его «спасал» завышенный порог strong; сейчас — балл 88.1
  ниже 93. Fake-модель всё ещё не умеет рассуждать о зарплатных ожиданиях и
  риске удержания; для реальной LLM это отдельный вопрос.

### 6.2. Precision/recall 1.000 — это не качество продукта

* **Выборка синтетическая и маленькая.** 25 сценариев — покрытие, а не
  случайная выборка откликов с HH/Avito. На 25 случаях один FP меняет precision
  на 0.1; доверительный интервал широкий.
* **Разметку и правила писал один человек.** Совпадение 25/25 по must-have
  частично объясняется тем, что новые случаи и новые правила создавались в одной
  итерации; межразметчицкого согласия нет.
* **Fake-модель не «понимает» резюме.** Это детерминированная эвристика на
  правилах: она не читает смысл, не различает тонкие формулировки («участвовал»
  vs «руководил»), не знает контекста компаний. Её цифры — нижняя граница и
  проверка harness, а не точность реальной LLM.
* **Промпт v2 этими цифрами не проверяется.** Fake не использует промпты
  вообще: метрики доказывают, что harness, quality-gate, правила вердикта и
  эвристика заглушки работают, но не что реальная LLM стала лучше. Для промпта
  есть только структурные тесты; нужен прогон на реальной модели.

### 6.3. Технический долг

1. В репозитории остаются **две fake-модели**: продуктовая
   `adapters/llm/fake.py` и тестовая `testing/fakes.py`. Harness теперь мерит
   продуктовую, но дублирование эвристик — источник будущих расхождений.
2. `hirebot evaluate` в CI ещё не включён. Публичный API готов: `load_dataset` +
   `run_evaluation`; осталось добавить job и порог деградации.
3. `expected_must_have_gaps` у quality-gate-случаев заполняется всеми
   обязательными критериями: это честно («данных нет»), но не различает
   «не подтверждено» и «опровергнуто». Для реальной LLM стоит разделить эти
   состояния.
4. По-прежнему нет замера на реальной LLM: стабильность при `temperature=0.2`,
   устойчивость к инъекциям, согласие с человеком на 100+ случаях.

## 7. Что делать дальше

1. **Прогнать набор на реальной LLM** через `container_factory` и
   `build_case_container(..., llm=real_llm)`. Сравнить не только цифры, но и
   стабильность ответа.
2. **Расширить выборку до 100+ случаев** и провести разметку двумя людьми,
   считать agreement. Отдельно стратифицировать: seniority, язык резюме, тип
   опыта (коммерческий/учебный/фриланс), инъекции.
3. **Свести fake-модели к одной реализации**, чтобы harness и демо мерили ровно
   тот код, который работает в проде.
4. **Включить `hirebot evaluate` в CI** и падать при деградации
   precision/recall/verdict accuracy ниже согласованных порогов.
5. **Проверить промпт v2 на реальной модели**: доля критериев с непустым
   `evidence`, доля evidence, найденных в тексте резюме, и влияние на must-have.
6. **Добавить в выборку пары с пограничным стажем и защищёнными признаками**
   (уже есть `age-borderline-experience`; нужны национальность, семейное
   положение, адрес) и тест «признак не меняет ни один балл».
