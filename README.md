# hirebot — AI-рекрутер для массового подбора

Сервис закрывает верх воронки найма целиком:

```
отклик на hh.ru / Avito  →  разбор резюме  →  уточняющие вопросы в чате  →
приглашение на собеседование  →  слот из календаря Talantix  →  бронь и подтверждение
```

Главное отличие от существующих решений (см. [сравнение](docs/research/competitors.md)):
**оба канала на равных** и **автоматическая запись в календарь Talantix**, чего нет ни у FriendWork AI
(отдаёт `.ics` с ручным подтверждением и заканчивает работу статусом «Отобран»), ни у HireMate
(календарь не назван вовсе).

> **Статус.** Проект запускается и проходит сквозной сценарий **без единого внешнего ключа** —
> на fake-адаптерах. Реальные интеграции (hh.ru OAuth, Avito API, Talantix GraphQL) реализованы
> и покрыты тестами на моках, но требуют учётных данных и, для Avito, подтверждённого доступа к API.

```powershell
cd C:\projects2

# 2. Демо-прогон: вся воронка на fake-адаптерах, без сети и ключей

# 3. Проверка конфигурации
.\.venv\Scripts\python.exe -m hirebot.cli doctor

# 4. Замер качества скрининга на размеченной выборке (16 случаев)
.\.venv\Scripts\python.exe -m hirebot.cli evaluate

# 5. Пошаговый разбор: что происходит между откликом и встречей
.\.venv\Scripts\python.exe -m hirebot.cli walkthrough

# 6. Справочник критериев подбора: из чего выбирать критерии вакансии
.\.venv\Scripts\python.exe -m hirebot.cli criteria

# 5. Показать интерфейс с данными: наполнить базу и открыть /ui
.\.venv\Scripts\python.exe -m hirebot.cli seed
.\.venv\Scripts\python.exe -m hirebot.cli serve
# → http://127.0.0.1:8000/ui
```

## Интерфейс рекрутера

`hirebot serve` поднимает не только API, но и рабочий экран рекрутера —
`http://127.0.0.1:8000/ui`.

Что умеет:

* **очередь диалогов** со счётчиками по состояниям (новые, ждут ответа,
  выбирают время, нужен человек, назначено) и фильтром;
* **карточка кандидата**: оценка, вердикт, критерии с весами и **цитатой из
  резюме** по каждому, пробелы, вопросы для собеседования;
* **переписка** с автообновлением, ручное сообщение кандидату;
* **слоты из календаря Talantix** и бронирование одним нажатием —
  по конкретному времени, а не по индексу в сетке;
* кнопка «Забрать отклики» — тот же поллинг, что делает воркер по расписанию.

Решения по интерфейсу, которые стоит знать:

| Решение | Почему |
|---|---|
| Серверный рендеринг + обычные формы | работает **без JavaScript**, не нужна сборка фронтенда, страницы надёжны |
| Свой CSS и ~70 строк JS, без зависимостей | UI работает офлайн; CDN и npm-пакеты не нужны |
| Вход по ключу, подписанная кука, CSRF | интерфейс показывает ПДн кандидатов — открытым его оставлять нельзя |
| Формулировка «конфликта в календаре нет» | система не видит личные встречи вне Talantix |

При первом запуске без `HIREBOT_SECURITY__WEBHOOK_SECRET` UI открыт — это
допустимо только локально, и об этом висит предупреждение в шапке.

Чтобы интерфейс был не пустым, наполните базу демонстрационными диалогами:

```powershell
.\.venv\Scripts\python.exe -m hirebot.cli seed
```

`seed` создаёт компанию, вакансию с критериями и пять кандидатов с разными
исходами (сильный, средний, слабый, смежник, недоступное резюме). Балл и вердикт
считает **настоящий** `ScreeningService`, а не заглушка — то есть в интерфейсе
видны те же цифры, что были бы в продакшене. Схема локальной базы создаётся
автоматически при старте сервера.

## Что показывает демо-прогон

`hirebot demo` проходит воронку целиком на тестовых адаптерах. Три отклика —
три разных исхода, каждый из которых предусмотрен архитектурой:

```
Шаг 1. Сбор свежих откликов с hh.ru
  Найдено откликов: 3 | новых диалогов: 3 | пропущено как обработанные: 0
  Повторный поллинг создал новых диалогов: 0 — повторная обработка исключена

Шаг 2. Анализ резюме и первый контакт
  Алексей Петров: балл 90.1 -> strong_match | действие: invited
  Мария Смирнова: балл 40.0 -> weak | действие: human_review_weak
  Иван Кузнецов: скрининг недоступен (—) | действие: human_review_weak

Шаг 3. Кандидат отвечает — бот предлагает время
  Алексей Петров: «Да, интересно, готов обсудить детали.»
  №  Когда                                Менеджер
  1  пн, 01.01.2024 13:00 (Europe/Moscow) manager-1
  2  пн, 01.01.2024 14:00 (Europe/Moscow) manager-1
  3  пн, 01.01.2024 15:00 (Europe/Moscow) manager-1

Шаг 4. Выбор времени и запись в календарь Talantix
  Алексей Петров: «Подходит вариант 1, давайте в это время.»
  Собеседование назначено: пн, 01.01.2024 13:00 (Europe/Moscow)
  Встреча в календаре: talantix-meeting-1
  Бронь подтверждена перечитыванием встречи из календаря.
```

Что здесь важно по существу:

| Наблюдение | Что оно доказывает |
|---|---|
| повторный поллинг не создал диалогов | идемпотентность приёма откликов |
| у сильного низкий риск, у слабого — `human_review` | бот не принимает кадровые решения сам |
| третий кандидат с закрытым резюме не уронил прогон | штатная деградация вместо падения |
| слоты подобраны под занятость, время в зоне кандидата | работа с календарём и часовыми поясами |
| бронь подтверждена перечитыванием встречи | защита от «потерявшегося» ответа календаря |

Переписка, которую формирует бот (реальный фрагмент вывода):

> Здравствуйте, Алексей! Спасибо за отклик на вакансию «Python-разработчик».
> Резюме посмотрели — хочется обсудить детали на коротком созвоне.
> Вот время, где конфликта в календаре нет: …
> Напишите, пожалуйста, номер удобного варианта.

Обратите внимание на формулировку «конфликта в календаре нет», а не «время свободно»:
система видит занятость только внутри Talantix.

Проверка окружения перед запуском — `hirebot doctor`:

```
│ Каналы площадок    │ ВНИМАНИЕ │ ни один канал не включён (HIREBOT_HH__ENABLED / …)  │
│ База данных        │ OK       │ соединение установлено (sqlite+aiosqlite:///./…)    │
│ Redis              │ ВНИМАНИЕ │ недоступен; кэш, локи и лимиты деградируют          │
│ Календарь Talantix │ ВНИМАНИЕ │ выключен: автобронирование недоступно               │
```

## Скоринг в процентах и настраиваемые профили

Соответствие показывается **тремя числами**, потому что одно врёт:

| Показатель | Смысл |
|---|---|
| **процент** | взвешенное закрытие критериев вакансии |
| **уверенность** | какая доля веса критериев подтверждена данными |
| **блокеры** | провалы обязательных критериев — автоприглашение невозможно |

«78% при данных по 4 из 6 критериев» и «78% по всем шести» — разные кандидаты.

### Профиль скоринга: настройка под вакансию

Критерии, вопросы и пороги — **версионируемый профиль**, а не код:

```
/ui/vacancies → «Настроить критерии»
  Шаг 1. Критерии: галочка + вес 1–5 + «обязательный»
  Шаг 2. Вопросы кандидату: не больше 5, с привязкой к критерию
  Шаг 3. Пороги: пригласить / человеку / отказ
```

Решения по устройству:

| Решение | Почему |
|---|---|
| Галочка + **вес 1–5** + переключатель «обязательный» | чекбокса мало: два отмеченных критерия не должны значить «равны» |
| **Версии профиля** | изменение критериев не затрагивает уже обработанных; в решении хранится `profile_version` |
| **Shadow-режим по умолчанию** | первый запуск: система считает и показывает, но не отправляет |
| **Кэш привязан к версии профиля** | после смены критериев старый результат не переиспользуется |
| Валидация на сервере | несогласованный профиль нельзя отправить через API |

### Вопросы: максимум 5

Вопрос задаётся, только если его ответ **может изменить решение**. Это
проверяется интервалом неопределённости: если даже при худшем ответе процент
остаётся выше порога, спрашивать нечего.

Стоп-правила: лимит 5, решение стабильно, найден блокер, два непонятных ответа,
кандидат попросил не спрашивать, нет ответа 24 часа.

### Приоритизация: кому писать первым

Приоритет — **взвешенная сумма объяснимых вкладов**, а не «магическая» поправка:

```
priority = 0.70×процент + 0.15×уверенность + 0.10×свежесть + 0.05×доступность
```

Блокер не вычитает балл, а **запрещает автоприглашение**. В карточке видно
вклад каждого фактора.

```bash
hirebot criteria            # справочник 43 критериев
GET /api/v1/queue           # очередь по приоритету
GET /api/v1/vacancies/{id}/scoring
```

## Очередь подтверждения: почему бот безопасен для реальных кандидатов

Включается одной настройкой — `HIREBOT_POLICY__REQUIRE_HUMAN_APPROVAL=true`.

```
отклик → скрининг → бот решает, что ответить, и пишет текст
                 ↓
        черновик в очереди «На подтверждении»
                 ↓
   рекрутер читает / правит / отклоняет → одна кнопка → отправка
```

Что это даёт:

| Без подтверждения | С подтверждением |
|---|---|
| бот пишет кандидату сам | кандидат ничего не получает до решения человека |
| ошибка модели уходит кандидату | рекрутер видит текст **и причину**, почему бот его предлагает |
| — | рекрутер может отредактировать формулировку — уходит его версия |
| — | черновик хранит модель и версию промпта: видно, чем он создан |

Технические гарантии:

* **один ожидающий черновик на диалог** — новый вытесняет старый (частичный
  уникальный индекс в БД), поэтому одобрить устаревшее сообщение нельзя;
* **отправка идемпотентна** — ключ тот же, что при прямой отправке: повторное
  нажатие не отправит кандидату второе сообщение;
* **отклонение ≠ отказ кандидату** — диалог остаётся человеку в `HUMAN_REVIEW`;
* черновик создаётся **без обращения к площадке**: если канал недоступен, работа
  не останавливается.

Управление: экран `/ui/approvals`, API `GET /api/v1/approvals` и
`POST /api/v1/approvals/{id}/approve|reject`, CLI:

```powershell
hirebot approvals list
hirebot approvals approve <id> --text "исправленный текст"
hirebot approvals reject <id> --reason "не подходит по опыту"
```

## Персональные данные (152-ФЗ)

```powershell
hirebot privacy purge --dry-run   # показать сроки хранения
hirebot privacy purge             # удалить то, что просрочено
hirebot privacy export <id>       # выгрузить все данные кандидата
hirebot privacy erase <id> --yes  # удалить ПДн по требованию
```

Сроки задаются в `HIREBOT_PRIVACY__*` (резюме — 180 дней, переписка и скрининг —
365, журнал — 730). Удаление по требованию сохраняет воронку: диалог и бронь
остаются, имя и контакты — нет.

## Как это устроено

```
                 ┌────────────────────────────────────────────┐
   HTTP/вебхуки ─┤  api/        FastAPI: вебхуки, админ-API     │
   ARQ / inline ─┤  worker/     фоновые задачи и cron-поллинг   │
                 ├────────────────────────────────────────────┤
                 │  services/   воронка, скрининг, диалог,     │
                 │              расписание, политики, outbox   │
                 │      │                                      │
                 │      ▼                                      │
                 │  domain/     сущности, FSM, ошибки  (нет I/O)│
                 │      ▲                                      │
                 │  ports/      протоколы-контракты            │
                 ├────────────────────────────────────────────┤
                 │  adapters/            │  infra/             │
                 │  hh  avito  talantix  │  db  http  cache    │
                 │  llm                  │  locks  queue       │
                 └────────────────────────────────────────────┘
```

Ключевые решения (подробно — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)):

| Решение | Зачем |
|---|---|
| **Порт `ChannelPort`** для каждой площадки | сервисы воронки не знают, откуда пришёл кандидат; третья площадка = один новый файл |
| **Действия по `actions[]` от hh.ru** | пути и методы не хардкодятся — API может их менять |
| **Транзакционный outbox** | «записать сообщение + сменить состояние + запланировать отправку» — атомарно, без потерь и дублей |
| **`idempotency_key` на каждом исходящем действии** | ретрай после таймаута не отправляет кандидату второе приглашение |
| **Single-flight обновление токенов** | refresh-токены hh.ru и Talantix одноразовые: параллельное обновление убивает сессию |
| **Взвешивание критериев на нашей стороне** | модель отдаёт оценки по критериям, итоговый балл считаем мы — ответ LLM не является истиной |
| **Policy Guard** | запрет автоотказа, тихие часы, лимиты, чёрный список защищённых признаков |
| **Деградация вместо падения** | нет Redis → память, нет arq → inline, нет канала → пустой результат, нет LLM → диалог уходит человеку |

Подробности про подводные камни каждой площадки: [docs/ARCHITECTURE.md, раздел 6](docs/ARCHITECTURE.md#6-подводные-камни).

## Честные ограничения

Это важно зафиксировать до пилота, а не после:

1. **Avito — риск, а не функция.** Доступ к Avito API выдаётся по заявке и подтверждается модерацией.
   Парсинг и автоматизация интерфейса запрещены условиями площадки. Пока доступ не подтверждён,
   сбор откликов с Avito работать не будет, и обещать его нельзя.
2. **hh.ru требует модерации приложения** (до 15 рабочих дней) и допускает только OAuth-токены —
   хранение логина и пароля пользователя прямо запрещено условиями API.
3. **Talantix API доступен на определённых тарифах**, токены выдаёт администратор. Требуется
   подтверждение тарифа заказчика.
4. **Личные встречи вне Talantix не видны.** Система не знает про занятость, не занесённую в CRM,
   поэтому кандидату никогда не пишется «время свободно» — только «конфликта в календаре нет»,
   и предлагается 2–3 варианта.
5. **Юридический контур.** Обработка персональных данных — 152-ФЗ (шифрование, минимизация,
   сроки хранения); автоотказ по защищённым признакам запрещён на уровне кода (ст. 3 ТК РФ,
   ст. 13.11.1 КоАП РФ); передача ПДн в зарубежную LLM — трансграничная передача, поэтому
   по умолчанию `LLM__SEND_PII=false`.
6. **UI рекрутера не входит в текущий объём** — сейчас API и CLI.

## Лицензия и использование

Проект создан как тестовое задание. Перед промышленной эксплуатацией необходимо:
получить подтверждённый доступ к API площадок, согласовать обработку ПДн с юристом,
выбрать LLM-провайдера с учётом 152-ФЗ и провести пилот на ограниченном числе вакансий.
